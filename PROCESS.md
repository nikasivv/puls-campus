# Как создавался ПУЛЬС с ИИ: черновик отчёта для конкурсной заявки

> Важно: здесь фиксируются фактически выполненные этапы из данной беседы и доступные артефакты. Это **черновик**, а не выдуманный дневник разработки. Перед отправкой в конкурс добавьте снимки работающего сайта, редактора кода, терминала с реальными результатами тестов и ссылки на конкретные сообщения/диалоги.

## 1. Проблема и продуктовая идея

Студентам неудобно искать расписание, оценки, справки и объявления в разных каналах. Обычный портал показывает формальный статус «Готова», хотя реальный документ может не быть выдан. Цель — соединить информацию, действия и фактический результат в едином личном кабинете.

**Уникальная продуктовая механика:** «Маршрут решения» с реальными стадиями, уточнениями, журналом действий, отменой/исправлением и выдачей результата. Блок «Твой ход» на главной называет следующее конкретное действие студента. Расписание едино для всей группы, поэтому созданный аккаунт получает занятия автоматически.

Решение не предполагает реальное подключение к вузовским ИС, официальные документы, электронные подписи, настоящие оценки или персональные данные.

## 2. Использованные инструменты (фактические)

| Инструмент | Для чего |
| --- | --- |
| ChatGPT / GPT-6 | Анализ ТЗ и пользовательских замечаний, проектирование ролей и процессов, генерация/исправление Python, HTML, CSS, тестов, документации, ревью ошибок |
| Python | Серверная логика Flask, SQLite, генерация PDF (ReportLab), автоматизированные проверки |
| Jinja2 | Компиляция и проверка HTML-шаблонов |
| Playwright + Chromium | Рендеры HTML-шаблонов с искусственным контекстом на 360/1280 px и проверка горизонтального переполнения |
| PyMuPDF | Проверка фактически сформированного PDF, извлечение текста и визуальный рендер |
| Командная строка / Python compileall | Синтаксические проверки |

**Не использовались:** реальные MCP-интеграции с университетом, платные API языковых моделей внутри приложения, Google Fonts/CDN, фиктивные результаты опросов студентов. Инструменты, IDE или модели, которые фактически использовала команда вне этого чата, добавьте самостоятельно, если такие были.

## 3. Ход разработки и ключевые промпты

1. **Создание концепта.** Запрос участника: «полностью все с нуля сделай, придумай какой нибудь отличающий дизайн нас от всех, все проверь по критериям… если нет в тз языка, то питон + css, html». Результат: Python/Flask, HTML/CSS, SQLite, фирменный визуальный стиль «ПУЛЬС».
2. **Исправление UI и ролей.** Участник приложил скриншот со слипшимися метками аудитории и изменения расписания и попросил быстрый вход в демоаккаунты. Снимок исходной ошибки: `evidence/01_schedule_tags_before.webp`. Исправление: flex-wrap, ограничение ширины меток, демовход одной кнопкой.
3. **Реальный жизненный цикл аккаунтов.** Запрос «а создание аккаунтов или еще что то, и так как они бы реализовывались в вузе». Добавлены администратор, группы, роли, блокировка, временные пароли.
4. **Критическая ошибка бизнес-процесса.** Скриншот сотрудника с выбором статуса «Готова», вопрос «а вот что я сделаю если нажму готова, ей же не пришлется ничего». Снимок исходного состояния: `evidence/02_done_without_delivery_before.webp`. Выявлен статус без результата.
5. **Сквозной аудит.** Запрос: «сделай, а также еще раз просмотри весь путь есть ли где такие же пропуски… нужно что то индивидуальное, не бесполезное и главное работающее». Внесены выдача PDF, обязательный результат для завершения, уточнения, ответ студента, история, отмена, отзыв неверного документа, групповое расписание, обновление оценок, уведомления и негативные проверки.

## 4. Ошибки, обнаруженные в процессе, и их исправления

| Ошибка / пробел | Что изменено |
| --- | --- |
| Метки аудитории и переноса переносились неправильно | `.lesson-tags` использует flex-wrap и гибкую компоновку |
| Завершение обращения без справки | Для справки создаётся и сохраняется PDF; общий запрос завершается только с ответом или PDF |
| Сотрудник просит уточнение, но студент не может ответить | Добавлены сообщения, статус «Требует уточнения», форма ответа и возврат в работу |
| Завершён неверный документ, исправить невозможно | Сотрудник может отозвать результат и вернуться к обработке; прежняя копия больше не скачивается |
| Созданному студенту неоткуда взять расписание | Единая таблица `group_lessons`; расписание определяется группой |
| Перенос касается одного студента | Обновление занятия для всей группы + уведомления |
| «Готова» из старой v3 без результата | При миграции возвращается в «В работе» |
| Сложно проверить роли | Две демороли студента + деканат + админ; быстрые кнопки и негативные тесты |
| Можно прикрепить испорченный файл с расширением `.pdf` | Проверка PDF через pypdf, размера и количества страниц |

## 5. Архитектура простыми словами

- **Пользователи и вход:** SQLite `users`, хеши паролей Werkzeug, защищённые cookie Flask, CSRF на POST-запросах. Демо-кнопки разрешены только для четырёх вымышленных аккаунтов при `DEMO_MODE=1`.
- **Расписание:** `academic_groups` + `group_lessons`; студент видит расписание своей группы. Деканат изменяет занятия группы, отправляет адресные уведомления.
- **Успеваемость:** `grades` с `user_id`; студент видит только своё. Сотрудник может изменить учебный результат в прототипе, действие фиксируется в журнале.
- **Заявки:** `requests`, `request_history`, `request_messages`, `request_documents`. Любое изменение на сервере проверяет роль и допустимый переход. Результат — PDF BLOB или текст ответа.
- **Уведомления:** `notices` с возможной ссылкой на связанную заявку, `notice_reads` для отметки прочтения.
- **Администрирование:** `academic_groups`, `users`, `audit_log`; у каждого действия проверяются разрешения.

## 6. Фактическая проверка

Проведены: компиляция Python, разбор всех Jinja2-шаблонов, независимый запуск основной бизнес-логики через локальный stub-тест без Flask, создание/открытие русского PDF, 360/1280 px визуальные рендеры восьми шаблонов без горизонтального переполнения. Подробности в `QA.md`.

**Не выполнено в среде подготовки:** HTTP-интеграционные тесты Flask — библиотеку Flask не удалось установить из-за блокировки DNS доступа к PyPI; интерактивное тестирование сайта в браузере под работающим Flask; развёртывание публичного адреса в России; запись видео. Все эти шаги нужно выполнить до конкурсной сдачи. Отсутствие ошибки в статическом рендере не доказывает работу всех серверных сценариев.

## Этап v5: сквозная переработка расписания и зачисления (22.11.2026)

Пользователь нашёл: стрелка аудитории выглядит ссылкой, хотя не ведёт никуда; у расписания нет реальных дат, а при редактировании нужно вручную вводить время; непонятно, когда получены оценки; уведомления занимают отдельную навигацию; кабинет деканата смешивает обращения и занятия; создание студентов не связано с подтверждением зачисления.

**Решение и поставленные ИИ задачи:**

1. Перенести групповое расписание на ISO-чётность недель и реальные даты, выделить точечные изменения в самостоятельную таблицу; не терять старые записи при миграции.
2. Ввести общую «сетку звонков» с номерами пар. У формы составления недели должны быть выбор группы, чётность, день, номер пары, предмет, преподаватель и аудитория. Отдельное действие — «сделать обе недели одинаковыми» с явным подтверждением.
3. Сделать карточки занятий раскрываемыми, убрать ложную стрелку у аудитории, добавить реальный календарь и колокольчик с непрочитанными событиями.
4. Разделить текущий контроль и архив результатов, демонстрационные июньские результаты показывать как закрытый весенний семестр.
5. Администратору добавить двухэтапный CSV-реестр: валидация, предпросмотр, ручное подтверждение, индивидуальные ссылки активации, запрет саморегистрации.
6. Упаковать чистый проект, сохранить документацию и тесты; разделять фактически выполненные проверки от HTTP/хостинга, которые без сети недоступны.

**Проверки и исправления ИИ:**

- Первый прогон показал, что новые номера пар не присваиваются при создании базы, поскольку миграция срабатывала до переноса старых занятий. Порядок миграции исправлен, повторный запуск проверен.
- Синтаксический анализ Jinja выявил конфликт `col.items` с методом словаря Python. Исправлено на `col['items']`.
- Правка регулярной пары из режима «обе недели» в «нечётная» могла удалить её из чётной. Добавлено разделение с сохранением исходной записи на противоположной неделе.
- Уточнена проверка повторных замен одной конкретной даты: сверяем с регулярным шаблоном, а не уже изменённым календарём.
- Прогнаны 9 изолированных тестов, offline smoke SQL и сравнение исходной базы v4 с мигрированной v5. Проверены предварительные рендеры в Chromium на ширине 360 и 1280 px. HTTP-тесты отложены до фактического запуска Flask (в текущей среде пакет недоступен).

Фактические кадры опубликованной версии ещё необходимо добавить перед сдачей; изображения в `design_previews/` являются статическими рендерами, а не доказательством работы с настоящим сервером.

## v6 — подробная карточка занятия по пользовательскому примеру

Пользователь указал, что короткая карточка должна показывать **тип занятия, номер пары, время, дисциплину, аудитории и преподавателей**. По нажатию «Подробнее» требуется **дата, несколько групп, аудитории и преподаватели**. Простая декоративная подстановка меток здесь была бы ошибкой: если карточка указывает несколько групп, занятие действительно должно присутствовать в расписании каждой из них.

Поэтому реализованы связанные записи регулярного занятия (`shared_id`) для каждой учебной группы и массивы преподавателей/аудиторий (`teachers_json`, `rooms_json`). Старые поля и БД сохранены для совместимости. Деканат выбирает тип, преподавателей, аудитории и группы при создании или изменении занятия, а календарь строит список групп по реально связанным записям. Для разового изменения связь учитывает выбранную дату и не создаёт ложного впечатления, что отмена в одной группе касается всех.

Для интерфейса создана доступная диалоговая панель с полным составом занятия. Мобильный формат проверен без горизонтального переполнения. Использованы Python для логики, Jinja/HTML для шаблонов, CSS для дизайна и нативный `<dialog>` с небольшим JS. Показанные в дизайне имя преподавателя и аудитории — вымышленные. Статические предпросмотры не подменяют проверку настоящего Flask-приложения.
